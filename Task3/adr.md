### **Название задачи:** Концептуальная архитектура MVP для открытия депозитов онлайн

### **Автор:** Архитектор команды цифровой трансформации

### **Дата:** 25.07.2025

### **Функциональные требования**

| :-: | :- | :- | :- |
|1|Клиент, Сайт|Подача заявки на депозит на сайте|1. Клиент заходит на сайт банка<br>2. Просматривает информацию о доступных депозитах с актуальными ставками<br>3. Заполняет форму заявки, указывая ФИО и телефон<br>4. Отправляет заявку<br>5. Получает подтверждение о принятии заявки|
|2|Клиент, Интернет-банк|Подача заявки на депозит в интернет-банке|1. Клиент авторизуется в интернет-банке<br>2. Переходит в раздел "Депозиты"<br>3. |3|Сотрудник кол-центра, Система кол-центра|Обработка заявки с сайта|1. Сотрудник кол-центра получает уведомление о новой заявке<br>2. Просматривает данные заявки<br>3. Связывается с клиентом<br>4. Консультирует по условиям депозита<br>5. Регистрирует результаты звонка в системе|

|5|Сотрудник бэк-офиса, Система управления ставками|Управление ставками по депозитам|1. Сотрудник получает данные о текущем уровне кредитного риска<br>2. Входит в систему управления ставками<br>3. ### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
|1|Доступность сервисов 24/7 с показателем 99,9%|
|2|Время отклика по всем операциям должно быть в миллисекундах|
|3|Защита чувствительных данных механизмом шифрования трафика|
|4|Минимизация нагрузки на базу данных АБС|
|5|Использование существующих технологий (MS SQL, Oracle)|
|6|Избегание прямой интеграции интернет-банка с API АБС|
|7|Время загрузки справочных данных менее 1 секунды|
|8|Соответствие интерфейсов принятой в компании системе дизайна|
|9|Горизонтальное масштабирование и распределение запросов|
|10|Подготовка к переходу на микросервисную архитектуру для интернет-банка|

### **Решение**
Для реализации MVP открытия депозитов онлайн предлагается следующая концептуальная архитектура:

**Ключевые компоненты архитектуры:**

1. **Сервис управления депозитами** - новый микросервис, который будет обрабатывать заявки на открытие депозитов. Он будет разработан на Java Spring Boot и развернут в существующей инфраструктуре банка. Сервис будет взаимодействовать с АБС через специальный интеграционный слой.

2. **Интеграционный слой** - промежуточный компонент, который будет абстрагировать прямое взаимодействие с АБС. Он позволит снизить нагрузку на АБС и обеспечит буферизацию запросов.

3. **Сервис управления ставками** - компонент, который будет хранить и управлять ставками по депозитам. Он заменит текущий процесс с Excel-файлами и обеспечит централизованное хранение и распространение информации о ставках.

4. **Брокер сообщений** - для асинхронного обмена данными между компонентами будет использоваться брокер сообщений на базе RabbitMQ (как альтернатива Kafka, учитывая несовместимость с текущей версией интернет-банка).

5. **API Gateway** - компонент, который будет маршрутизировать запросы от клиентских приложений к соответствующим сервисам.

**Интеграции:**

1. Сайт будет взаимодействовать с сервисом управления депозитами через API Gateway.
2. Интернет-банк будет взаимодействовать с сервисом управления депозитами через API Gateway.
3. Сервис управления депозитами будет взаимодействовать с АБС через интеграционный слой.
4. Сервис управления ставками будет предоставлять данные о ставках для сайта, интернет-банка и АБС.
5. Система кол-центра будет получать заявки с сайта через брокер сообщений.
6. SMS-шлюз будет использоваться для отправки уведомлений и кодов подтверждения клиентам.

**Логика принятия решений:**

1. **Микросервисная архитектура для новых компонентов** - позволит подготовить интернет-банк к переходу на микросервисную архитектуру и обеспечит гибкость при разработке новых функций.

2. **Использование брокера сообщений** - обеспечит асинхронное взаимодействие между компонентами и снизит связанность систем.

3. **Интеграционный слой** - решает проблему перегрузки АБС, изолируя прямое взаимодействие с ней.

4. **Сервис управления ставками** - централизует управление ставками и устраняет необходимость в ручном обмене Excel-файлами.

5. **Использование существующих технологий** - сервисы будут разработаны с использованием технологий, в которых у сотрудников банка уже есть экспертиза (Java, Spring Boot, MS SQL).

### **Альтернативы**
1. **Прямая интеграция интернет-банка с АБС** - отклонена из-за риска перегрузки АБС и ограничений по масштабированию.

2. **Полный переход на микросервисную архитектуру** - отклонен из-за высокой сложности и рисков при полной перестройке существующих систем.

3. **Использование Kafka вместо RabbitMQ** - отклонено из-за несовместимости с текущей версией интернет-банка.

### **Недостатки, ограничения, риски**

1. **Ограничения интеграционного слоя** - может стать узким местом при высокой нагрузке.

2. **Временная синхронизация данных** - может возникнуть проблема с актуальностью данных между разными системами.

3. **Сложность миграции данных** - перенос данных о ставках из Excel-файлов в новую систему может потребовать дополнительных усилий.

4. **Зависимость от SMS-шлюза** - в случае сбоев в работе SMS-шлюза клиенты не смогут подтвердить операции.

5. **Ограничения по вертикальному масштабированию АБС** - даже с интеграционным слоем АБС остается потенциальным узким местом системы.

6. **Необходимость обучения персонала** - сотрудникам потребуется обучение для работы с новыми системами.
